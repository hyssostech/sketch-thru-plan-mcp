# STP-1805 handoff: tool descriptions and instructions for the STP-1476 user stories

Branch `claude/STP-1805-mcp-descriptions`, from `claude/STP-1804-mcp-512-sync` @ 9a574de. Work commit 7e1dcae;
this handoff is the commit after it. No PR (per brief). `npm test`: 201/201 in 15 files (was 195/14), and the
search-eval floor is unchanged (73/73, floor 0.98).

## What changed

- **stp-live instructions** (`packages/live/src/routing.ts`). Built per write mode from `SYMBOL_ROUTES`
  (`routing.ts:19`) and wired in at `packages/live/src/server.ts:215`.
  - `CODE_SOURCE_RULE` (`routing.ts:39`), in every mode: codes come from the user's data or files, or from STP
    (an existing object, SearchSymbol), never from the model. 2525C maps to 2525D, never the reverse; an empty
    charlieSidc means no 2525C code exists.
  - Read-only mode: a code question is a lookup (SearchSymbol, GetPoidObject, GetScenarioContent) that names its
    source. SearchSymbol codes are a symbol type's codes, not a finished symbol.
  - Write and destructive modes route by input:
    - words: SendSimulatedSpeechRecognition with SendPenDown and SendInk; "Do not use AddSymbol for it".
    - data: AddSymbol "with each code exactly as given", or the imports. In write mode the imports are not listed,
      so the text says STP_DESTRUCTIVE=1 lists them.
    - a rejection: report the outcome and reason, never swap in an invented code.
    - mixed: do both, and name existing objects by poid.
  - An audience line goes into every mode.
- **Knowledge server instructions** (`packages/knowledge/src/server.ts:90`, `KNOWLEDGE_INSTRUCTIONS`); there were
  none before.
  - Help depth: integrators get methods, params, events and failure modes; end users get what to say, draw or
    click, in planning terms, with no JSON-RPC. The docs are written for integrators, so translate.
  - The code-source rule for help answers.
- **Eval** (`packages/live/eval/tool-choice-eval.json`, `packages/live/test/tool-choice-eval.test.ts`).
  - 15 cases in 7 pairs that differ in input (words, data, mixed, lookup) or audience. Each case lists its
    `use`/`avoid` tools and its steering facts.
  - A fact is a set of regexes over one text: the live instructions for a mode (read from a real server over
    MCP), the knowledge instructions, or a contract tool's description or edge cases.
  - Hard checks: the set is well-formed and paired. Every `use` tool is listed in its mode and named in the
    instructions. Instructions never name a routed tool that the mode does not list. Every fact with owner `mcp`
    holds.
  - Scored: the share of cases whose facts all hold, 11/15 = 0.733, against floor `PASS_FLOOR = 0.73`
    (`test:27`), which only goes up. The 4 cases short are contract-owned gaps, printed as `GAP ... [proposal: X]`.
  - Why no model call: CI must be deterministic, and the instructions are the guidance a model reliably has in
    context before it picks a tool (comment 15340). The eval asserts that the steering facts are present. It
    cannot assert that a model obeys them; a live-model run would be a separate, manual check.
  - `packages/live/package.json` gained a devDependency on `stp-mcp-knowledge` (the test reads its
    instructions), and the lockfile changed with it.
- **Proposal** `docs/proposals/STP-1805-contract-wording.md`: current, proposed and why, per method, for
  AddSymbol, SendSimulatedSpeechRecognition and SearchSymbol. SearchSymbol covers the /symbol-index.json
  route, `<path>` changing to `<source>` (path or URL) in the edge case, and what its codes are. With all of it
  adopted, the eval scores 15/15.
- The README has a new subsection, "Instructions: where symbol codes come from", under the Live-STP server.

## Withdrawn items respected (comment 15346)

- 2525C-only AddSymbol is not refused.
- There is no global "describe, don't encode" rule.
- Data or integrator input is never redirected to recognition.
- There is no STP_TOOLS setting.

## Open decisions

1. **Description overlay** (MCP-side sentences appended to contract descriptions). It is not built: the brief
   said to ask first. Its trade-offs are in the last section of the proposal.
2. **Upstream adoption.** The proposal needs to go into sketch-thru-plan-sdk-js, after its PR 165, and the bridge
   copy. Then: `npm run contract:update`, `npx vitest run -u`, and raise `PASS_FLOOR`.
3. **SearchSymbol codes and echelon.** Does the shipped index's deltaSidc carry an echelon? The fixture is
   synthetic. The wording avoids saying either way.
4. **2525C-only AddSymbol.** The outcome should explain that the engine ignores it (15346). That needs a captured
   edge case before V10 can name it.
5. **A `stp-live://routing` resource.** The route table could also be exposed as a resource. Not done: the
   instructions are what a model sees first.
6. **There is no `recognize` intent tool yet** (comment 15340, measure 5). The words route uses the raw
   recognition methods. If one is added later, add it to `SYMBOL_ROUTES` and the eval.
